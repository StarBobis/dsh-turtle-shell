# dsh-turtle-shell · 叠甲协议

装一次，DSH 的每一条回复都按「证据等级 + 限定动作 + 出口标记」来写。左侧栏一枚龟壳图标，点开是总开关、三档密度、协议原文和注入自检。

叠甲不是给每句话加「可能」，而是给**每一段**加三层可检查的结构：

```
L2 <论断>；这只能说明 A，不能说明 B；仅在 C 条件下成立。→ 结论
└等级┘ └──── 限定动作（按档位：1 个 / 2–3 个 / 连续嵌套）────┘
```

## 装之前 / 装之后

### 同一个问题，两种答法

**问题**：面板上说「改完下一条消息生效」，也就是「一关，下一条消息立刻不带协议」，准确吗？

**装插件之前（默认文风）**

> 真的，立刻生效。`text` 是函数，每次组装都重新算，关掉就返回空串，模型自然看不到。

**装插件之后（分析档）**

> L2 「关掉就立刻不带」在注入层面成立：`src/host.js` 的 `text` 是函数，agent 的 `preStep()` 每次都会 `await systemPrompt.assemble()`，函数因此被重新求值；关闭后返回 `''`，渲染时被 `filter(text => text.length > 0)` 丢掉。这只能说明「下一次组装结果里没有这段文本」，不能说明「模型下一轮一定不按叠甲写」——提示词不是校验器。
>
> L0 「下一条消息」这个时间点我按代码推：`assemble()` 发生在 preStep，跨消息时下一次 step 就是下一条消息；但同一轮里多步时第二步就变了，所以「一条消息只变一次」是错的。
>
> 结论：注入层面 L2 成立；回复文风层面要打 L4，得看真实下一轮的输出。

差别不在字数，而在三个能指认的位置：段首多了等级，句中多了「只能说明 / 不能说明」，句尾给了失效条件和结论。

### 一眼能对照的差异

| 场景 | 装之前 | 装之后 |
| --- | --- | --- |
| 段首 | 直接下结论 | `L0`–`L4` 或 `[无判断]` |
| 断言强度 | 「是 / 没问题」一句到底 | 观察、推断、证明分开，禁止跨级 |
| 限定句 | 「可能」「建议进一步确认」这类万能句 | 只认五类（见下），万能句判不合格 |
| 进度播报 | 「读完 X，发现 Y，下一步 Z」 | 同一行三槽位，「发现」槽必须带限定 |
| 没话可说 | 硬凑一句 | `[无判断]` + 一句理由 |
| 用户要短 | 照旧叠 | 首行 `[叠甲已按用户要求关闭]`，但下限不是 0 |
| 代码 / 日志 / 路径 | 一并叠 | 明确豁免，且清单是封闭列表 |

这些差异是**文本层面可检查**的：把一段回复按段落切开，逐段对表即可。它不保证模型一定遵守——协议是提示词约束，不是后处理校验器，插件也不改写模型输出。

### 读者侧的四条自检

1. 每段开头有没有 `L0`–`L4` 或 `[无判断]`？
2. 有没有至少一句「只能说明 X，不能说明 Y」/「仅在 Z 下成立」/「什么情况下不成立」？
3. 等级和措辞对得上吗（L2 说成「已生效」就是跨级）？
4. 限定句是不是「可能需要确认」这种能套在任何内容上的话？

四条都过，才是真的叠了；只变长、槽位齐全但零限定的，协议里单列为退化路径。

## 它是怎么叠的

### 1. 协议文本只有一个来源

`src/protocol.js`：`CORE` 写死 §0–§9，`buildProtocol()` 在末尾拼 §10 当前档位。Host 注入、面板「协议原文」、HTTP `/protocol`、测试全都读它，所以「面板看到什么」和「模型读到什么」不会分叉。

正文长度约 1.6k 字符；三档只差 §10 那一行，长度差在几十字符内。

### 2. 注入点是一个全局 systemPrompt section

`src/host.js` 里那段，省略统计计数后的骨架（原文用 `SECTION_NAME` / `SECTION_ORDER` 常量和 `activeText()` 包装，这里写成字面值）：

```js
ctx.systemPrompt.section({
  name: 'turtle-shell:protocol',
  order: 10300,
  text: () => (state.enabled ? buildProtocol({ tier: state.tier }) : ''),
  interpolate: false,
})
```

- `order: 10300` 接在内置的 `deployment:persona-suffix`（10200）之后。
- `text` 是**函数**，`assemble()` 每次都重新调用它（`@deepseek-ai/dsh-system-prompt` 的 `assemble()`：`typeof section.text === 'function' ? section.text(context) : section.text`）。agent 的 `preStep()` 每个 step 都会 assemble 一次，所以开关改完，下一次组装就变。
- 关闭时返回 `''`；渲染阶段 `renderPrompt()` 用 `filter(text => text.length > 0)` 丢掉空段。注意：section 本身仍留在注册表里，只是这次没有文本——所以看 `chars`，别只看 `found`。
- `interpolate: false`：协议正文里的花括号不会被当成 `{{变量}}` 插值。

### 3. 模型被要求以「段」为单位交付三件套

判定单位是自然语言段落：两次换段之间的连续文字都算，包括进度播报行、列表项、表格里成句的单元格、最后的结论段。每段必须同时有：

1. **等级前缀** `L0`–`L4`，或 `[无判断]`；
2. **至少 1 个具体限定动作**；
3. **达到当前档位的密度**。

缺一项就算不合格，要重写；不允许先写完再补一句。

### 4. 证据等级是硬刻度

| 等级 | 含义 | 典型证据 |
| --- | --- | --- |
| L0 | 推断 | 命名、结构、常识 |
| L1 | 编译 / 单测 | 语法检查、类型检查、单测通过 |
| L2 | 合成回读 | 自己构造输入、读回自己写的数据或自己调用的返回值 |
| L3 | 真实只读 | 读日志、读配置、查询状态 |
| L4 | 真实生效 | 真实用户路径跑通并有可复现证据 |

禁止跨级：L2 不能说成「已生效」，L3 不能说成「验证了系统正常」；也不许用「据观察」「已经清楚」「已验证」代替等级编号。

### 5. 什么才算限定动作（防注水的地方）

只有五类：

- **否定等价**：这只能说明 X，不能说明 Y；
- **范围收窄**：仅在 Z 条件下成立；
- **层级区分**：观察 / 支持 / 推断 / 证明 / 保证不是一回事；
- **替代解释**：同一现象至少还有 A 或 B 两种解释；
- **失效条件**：什么情况下这个结论会不成立。

「需要进一步确认」「具体情况具体分析」「可能存在风险」这类能套在任何内容上的句子明确判不合格。所以叠甲不是加免责声明，是把结论的边界写出来。

### 6. 出口和豁免

- 确实没内容可叠：段首 `[无判断]` + 一句理由，例如 `[无判断] 仅为工具调用参数说明`。
- 用户要求别叠：该条消息首行 `[叠甲已按用户要求关闭]`，之后按普通风格写。
- 豁免清单是封闭的：代码块内部、工具调用名称与参数、纯路径 / 数字 / 表格字段值的行、引用块、`[无判断]` 段、带关闭标记的整条消息。清单之外默认必须叠；觉得该豁免的，照常写完，再另起一行建议加进清单。

### 7. 五条禁止的退化路径

协议专门点名这些「看起来达标、实际没叠」的写法：结构达标但零限定；用自然语言冒充等级；只在结尾总结叠；用「这只是复述事实」跳过叠甲；把豁免清单当起点不断扩张。自检要求逐段过，不是整篇写完再过。

## 三档密度

| 档位 | id | 每段限定动作 | 面板文案 |
| --- | --- | --- | --- |
| 普通 | `normal` | 1 个 | 最低档，仍不允许整段免叠 |
| 分析（默认） | `analysis` | 2–3 个不同动作 | 同一句换皮重复不算「不同」 |
| 强叠甲 | `heavy` | 连续嵌套 | 允许嵌套，但必须正面回答原问题 |

三档改的是 §10 一行和它导出的密度要求，`CORE` 不变。任何档位的下限都不是 0：不存在「整段免叠」的档位。

## 生效范围

- 全局 section 会进入每一次 `systemPrompt.assemble()`：默认 preset、普通新会话、子代理都算。
- 例外：带 `complete: true` 的 agent preset（例如 Aurabot 私聊）在组装层会把自己变成**唯一** section，其它 section 被替换。这不是插件开关故障，是 `@deepseek-ai/dsh-system-prompt` 的既定语义（`completeSection === undefined ? transformed.sections : [completeSection]`）。
- 想绕开这个例外，只能把协议文本搬进那个 preset 自己的 persona；本插件不主动改别人的 preset。
- 注入 ≠ 遵守：模型可以不照做，插件也不做输出后处理。要判断某条回复是否执行了协议，看文本，不看开关。

## 面板

- **总开关**：开 / 关注入。面板文案写「下一条消息生效」，严格说生效点是下一次 `assemble()`（通常是下一条消息的 preStep）。
- **密度档位**：三选一，立即写盘。
- **协议原文**：展开看模型实际读到的全文。
- **自检注入**：调用一次 `systemPrompt.assemble()`，回读我们的 section 在不在册、字符数，以及本次组装的 section / context / tool 计数。这是 L2 合成回读，只证明组装层收到了文本，不证明某条回复已经按它执行；关闭时 `found` 仍为 `true`、`chars` 为 0，真正「没注入」发生在渲染阶段过滤空段。

## HTTP

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/turtle-shell/api/state` | 当前开关、档位、字符数、组装计数 |
| POST | `/turtle-shell/api/config` | `{ enabled?: boolean, tier?: string }` |
| POST | `/turtle-shell/api/reset` | 恢复默认（启用 + 分析档） |
| GET | `/turtle-shell/api/protocol` | 协议全文 |
| POST | `/turtle-shell/api/probe` | 真组装一次并回读 section |

## 安装

```
plugin_manager({ action: "install_bundle", target: "C:\\Dev\\dsh-turtle-shell" })
```

本地目录安装是链接到 checkout：

- 改了 Host 半边（`src/`）：需要重启 DSH 才会加载新的 ESM 代际——Node 按模块 URL 缓存，禁用 / 启用插件行不会重新执行模块。
- 改了网页半边（`client/`）：刷新页面即可；没有跑 `pnpm run dev:web` 时不会自动热更。

## 开发

```
node --check src/host.js
node --check client/client.js
node --test test/protocol.test.js test/client-contract.test.js
```

| 文件 | 职责 |
| --- | --- |
| `src/protocol.js` | 唯一文本来源：`CORE`、三档、`buildProtocol()` |
| `src/host.js` | 注册 systemPrompt section + `/turtle-shell/api/*` 路由 |
| `client/client.js` | 侧栏图标与主面板（原生 `createElement` 构建的 bundle） |
| `test/` | 协议的文本契约与 client bundle 的挂载契约 |

改协议文本只动 `src/protocol.js`；测试里的 `协议包含全部硬条款` 会卡住漏掉 L0 / L4 / `[无判断]` / 豁免清单之类关键条款的情况。
